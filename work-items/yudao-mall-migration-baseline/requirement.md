## 2. 背景与目标

### 2.1 背景

用户的原始目标是先迁移芋道商城代码，让当前项目的商城业务实际运行起来，再做二次开发。当前项目已存在商城代码、服务拆分、测试和前端适配，但历史交付中混有业务增强与可靠性设计；构建通过不能证明源项目能力已完整迁移，也不能证明实际环境业务已跑通。

本工作项不继续沿用“已有代码生成阶段完成，所以迁移已经完成”的判断。历史工作项只提供线索，必须以本地源代码、当前实现和真实执行结果重新核对。

### 2.2 已确认目标

1. **全量盘点、分批跑通**：盘点本地芋道商城及其必要会员、支付依赖能力，优先跑通核心交易闭环，再逐批完成其他源项目商城能力的验收。
2. **按源码基线收敛**：恢复或补齐必要业务逻辑；额外设计先归类说明，不因已经实现或已有测试就默认保留。
3. **本地隔离环境验收**：在独立开发环境启动当前项目并执行真实业务调用，不使用现有业务库做破坏性试验。
4. 保持当前项目技术栈和已确认架构边界，不把迁移变成重新设计商城或替换整个开发底座。

## 4. 需求范围

### 4.1 本次要做

1. 建立源项目到当前项目的能力映射清单，至少覆盖：
   - 商品：商品定义、分类、品牌、规格、库存、评价、收藏、浏览等实际存在的源能力。
   - 营销：购物车、优惠券、活动、商城装修及其他源项目商城能力，最终清单以源码盘点为准。
   - 交易：结算、订单、履约、售后及源项目其他商城交易能力。
   - 商城所需会员、认证、支付和退款等依赖链；不据此迁移芋道全部平台业务。
   - 管理端及小程序对应入口、权限、页面、接口和必要配置。
2. 将每项能力标记为：已迁移待验收、迁移缺失、业务行为不同、当前项目额外设计、必要架构适配或外部条件阻塞，并给出源码证据。
3. 核对字段、接口、状态、计算规则、调用归属和异常流程，不能仅比较类名、表数或接口数量。
4. 优先修复启动和核心业务链路阻塞，再按清单逐批补齐其余迁移能力。
5. 明确当前额外设计的来源和必要性，形成保留/简化/删除建议；会改变既有行为或跨服务协议的收敛，列清单确认后实施。
6. 准备本地隔离环境的配置与启动说明，并逐层记录实际运行证据。
7. 对每批业务改动补充对应回归，不删除测试或放宽断言来掩盖真实问题；源逻辑或已确认契约变化时，说明测试基线变化的依据。

### 4.3 已有设计与源逻辑冲突时的处理

先检查真实源码，再给出行为差异、调用方影响、数据影响和必要适配说明，不再基于对芋道的口头印象作决定。

当前已经明确的架构约束和用户决策不能以“与芋道保持一致”为由擅自撤销。对于此前已单独确认的补充能力，例如销量口径，列入差异清单核对，不自动删除，也不扩展为新功能。

对于已有消息表，必须把 Outbox 出站记录、Inbox 消费记录与业务台账分开列出；现存对象如何处理、是否涉及历史数据，属于收敛清单的明确决策，不用术语替换绕过用户要求。

## 5. 业务验收主线与推进顺序

### 5.1 核心闭环优先

管理端登录与必要配置
→ 商品维护并发布
→ 会员登录
→ 小程序浏览商品
→ 购物车或直接购买
→ 结算与适用营销规则
→ 建单及库存变更
→ 支付结果处理
→ 发货/源项目支持的履约方式
→ 确认收货
→ 订单评价。

并行验证异常分支：库存不足、重复提交、未支付关单及资源恢复、越权访问、支付结果重复/延迟、售后退款及资源处理。具体资格、金额、状态和库存行为按源码及已确认适配规则验收，不在需求阶段重新发明。

### 5.2 分批推进

| 批次 | 目标 | 可交付结果 |
|---|---|---|
| 基线与全量盘点 | 固定源码参考、建立功能与差异清单 | 每项可追溯到源码与当前实现，未知项明确标记 |
| 运行底座 | 明确独立库、中间件、配置、启动入口、权限和基础数据 | 相关服务启动、注册及基础访问有实际证据 |
| 核心交易闭环 | 跑通 5.1 的主线和必要异常分支 | 可复现操作步骤、实际请求与业务结果 |
| 其他商城能力 | 按全量清单逐批补齐和验收 | 不把“核心链路通过”替代“全部能力完成” |
| 迁移收口 | 明确剩余差异、阻塞项与二次开发清单 | 形成最终验收结论，不混淆已验证与未验证 |
